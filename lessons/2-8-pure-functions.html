2-8 — Pure Functions: Easy Testing Workshop

~70 minutes · Week 2, Day 2, 14:00–16:00 · Source: curriculum workshop pure-functions-easy-testing-ws, adapted solo

Why this matters: the week project brief (project.md) says in plain text: "You should have a pure functions" and "You should write a test for every function you have". This workshop is where you learn what makes that possible — a function you can't test easily is almost always a function that isn't pure.

Idea 1 — What makes a function pure

A function is pure when both of these hold:

  1. Same arguments → same return value, every time.
  2. No side effects — it does nothing but compute its return value. No writing to variables outside itself, no HTTP requests, no touching the DOM (the document.querySelector/textContent work from lesson 1-10).
const stringLength = (str) => str.length;   // PURE   — "hello" is always 5

const randomAdd = (x) => Math.random() + x; // IMPURE — rule 1 broken, a new answer each call

And the classic rule-2 break — a function that reaches outside itself and edits a variable it doesn't own:

let age = 1;                       // lives outside the function

const howOldNextBirthday = (a) => {
  age = a + 1;                     // side effect: it EDITS the outer variable
  return age;
};

howOldNextBirthday(age)            // 2
howOldNextBirthday(age)            // 3  ← the SAME line typed twice, different answer,
                                   //     because the side effect moved `age` underneath it

Why this decides how testable your code is: a test tells you which function is broken. If one test covers a big impure function that also mutates three globals and repaints the page, a red test tells you "something in here is wrong" — which is barely more useful than the bug report. Small pure functions give you the opposite: a failure names the one function to open. That's the whole argument, and it's why the workshop is called pure functions for easy testing.

The workshop's own snippets use var and function (x) { … }, and link to repl.it pages that no longer load; today we write const/let and arrow functions (1-7, 1-8) and run everything in Node or Jest instead.
More examples (optional)

Four functions. Two are pure, two are not — and the reason differs each time:

const total = (items) =>                       // PURE
  items.reduce((sum, i) => sum + i.price, 0);  // reads only its argument, returns a number
                                               // (reduce = 1-8's fold-into-one-value method)

const addTax = (price) => price * 1.16;        // PURE — arithmetic on the argument only

let cart = [];
const addToCart = (item) => {                  // IMPURE — mutates the outer `cart`
  cart.push(item);
  return cart;
};

const stamp = (note) =>                        // IMPURE — Date.now() changes every call,
  `${note} @ ${Date.now()}`;                   // so same argument ≠ same result

Note what is not on the impure list: console.log is technically a side effect (it writes to a terminal), but nobody counts it against you while debugging. The ones that bite are mutation, I/O, and the DOM.

Idea 2 — When the side effect is the point: split the function in two

Real apps must write to the DOM and to localStorage, so you can't ban side effects. You relocate them: one pure function that decides, one thin impure function that acts. You test the decision; the action is small enough to read and confirm by eye.

The workshop's Example 2 is an image whose opacity toggles. Impure version — reads a global, writes the DOM, then writes the global back:

let changeTransition = true;

const visionChange = () => {
  const img = document.getElementById("visionimage");
  if (changeTransition === true)  img.style.opacity = 0;
  if (changeTransition === false) img.style.opacity = 1;
  changeTransition = !changeTransition;        // outer variable, edited
};                                             // no arguments, no return value — nothing to test

Split in two. The decision becomes an argument in, a value out:

let isVisible = true;                             // the state lives out here, not inside a function

const visionChange = (visible) => !visible;       // PURE: the decision. true → false, false → true

const updateDom = (visible) => () => {            // returns a FUNCTION that does the effect
  const img = document.getElementById("visionimage");
  img.style.opacity = visible ? 1 : 0;            // show when visible, hide when not
};

isVisible = visionChange(isVisible);              // decide the next state (pure)
const applyIt = updateDom(isVisible);             // build the effect for that state
applyIt();                                        // ← the DOM is touched only here
The workshop README writes the same split but feeds updateDom the flipped value while keeping the original's opacity = 0 branch, which inverts the toggle, and it never writes the new state back to changeTransition — so the image never alternates. The version above fixes both. If you spotted it in the README before reading this, that is exactly the kind of eye the tests are meant to give you.

Now both halves are testable, and neither test needs a browser:

test("visionChange flips the boolean", () => {
  expect(visionChange(true)).toBe(false);
});

test("updateDom hands back a function", () => {
  expect(typeof updateDom(true)).toBe("function");
});

Hold this shape in mind for the ecommerce project (2-10): filterByCategory(products, category), cartTotal(items) and removeItem(cart, id) are pure and get tests; renderProducts(list) and saveCart(cart) are the thin impure edges that write to the page and to localStorage. That split is what makes "a test for every function" achievable instead of miserable.

One trap the workshop calls out in object-pass-by-reference.js: objects and arrays are handed to functions by reference (the reference-vs-value comparison from 1-7). So obj.x = 1 inside a function edits the caller's object — an invisible side effect. Copy first: const copy = { ...obj } or const copy = [...arr], using the spread operator from 2-6. That copy is shallow — objects nested inside the object are still shared — but nothing this week nests that deep.
More examples (optional)

The same decide/act split on a cart button, in the shape the project will need:

// PURE — takes the current cart, returns the NEXT cart. Original untouched.
const addItem = (cart, item) => [...cart, item];

// PURE — a number out of an array in, nothing else happens
const cartTotal = (cart) => cart.reduce((sum, i) => sum + i.price, 0);

// IMPURE, and deliberately boring: three lines, no decisions inside
const renderTotal = (cart) => {
  document.querySelector("#total").textContent = cartTotal(cart);
};

And the mutation trap, shown rather than described:

const badAdd = (cart, item) => { cart.push(item); return cart; };

const original = [{ price: 5 }];
const next = badAdd(original, { price: 9 });
original.length      // 2  ← the caller's array grew. Nobody asked for that.
next === original    // true — they are the same array, not two versions

Read more: javascript.info — object references and copying · MDN — Object.assign (the pre-spread way to copy, which you'll meet in older code)

Do it for real (~45 min)

You'll clone the curriculum workshop and refactor five impure functions until its five failing tests go green. The workshop's hard rule: you may not edit the test file. The tests define "pure" for you — make the code satisfy them.

  1. Clone the workshop into your code workspace (git clone is from 1-5; ~/code/ is the workspace convention from 1-4): 
    cd ~/code
git clone https://github.com/bootcamp-we-have-at-home/pure-functions-easy-testing-ws.git
cd pure-functions-easy-testing-ws
ls                       # exercises  test  object-pass-by-reference.js
                         # plus README.md, LICENSE, package.json, package-lock.json
    Success check: ls lists an exercises folder and a test folder.
  2. Install the dependencies — this repo already has a package.json listing Jest, so npm install just fetches what it names (2-2): 
    npm install              # creates node_modules/
                         # "19 high severity vulnerabilities" again — the 2-3 audit note
    You should see a line like added 300+ packages, a new node_modules folder in ls, and the same audit summary lesson 2-3 explained: the advisories sit inside Jest's own dependencies, and you must not run the npm audit fix --force npm suggests — it can swap Jest for a different major version and break the suite this workshop is about.
  3. Run the tests before changing anything, so you know your starting line (npm test runs the "test": "jest" script from package.json, as in 2-3): 
    npm test
    You should see Tests: 5 failed, 5 total — five red tests named "Refactor our x function so it is pure". All five failing is the correct starting state.
  4. Open this folder in your editor — File → Open Folder → ~/code/pure-functions-easy-testing-ws, since your editor is probably still on last lesson's project. Then read both files that matter: 
    cat exercises/exercise1.js      # the five impure functions — you edit THIS
cat test/exercise1.test.js      # what "pure" must mean — you do NOT edit this
    You should see a pattern repeated in every test: it calls your function, checks the return value, then checks that constantNumber/constantArray/constantObject is unchanged, then calls your function a second time expecting the same answer. That's rules 1 and 2 of Idea 1, written as assertions.
  5. Start Jest in watch mode in a second terminal tab (from 2-4) so every save re-runs the suite. The new tab starts in your home folder, so cd into the repo first (1-4) or npm/Jest will find no project here. It stays running and takes single-key commands — a re-runs all tests, q quits: 
    cd ~/code/pure-functions-easy-testing-ws   # the new tab starts in ~, not in the repo
npx jest --watchAll                        # stays running; press q to quit when you're done
    You should see the five failures, then a menu line Watch Usage: Press a to run all tests… and no prompt returning. Leave it open for the rest of the workshop. (Autosave is off — a save is what triggers the re-run.)
  6. Function 1, addOne. It currently takes no arguments and mutates the module-level constantNumber: 
    const addOne = () => {
  constantNumber += 1;     // side effect: edits a variable it doesn't own
  return constantNumber;
};
    The test calls addOne(4) and expects 5, and calls addOne(constantNumber) twice expecting 6 both times. Rewrite it to take a number and return a number, touching nothing outside. Save. Success check: the watcher flips test 1 to ✓ Refactor our addOne function so it is pure. and reports 4 failed, 1 passed.
  7. Function 2, timesTwo — the same disease, same cure: take the number as an argument, return the doubled value, leave constantNumber alone. Save. Success check: 3 failed, 2 passed.
  8. Function 3, incrementArray. This one does take an argument, but writes into it: 
    const incrementArray = (array) => {
  array.forEach((x, i) => {
    array[i] = x + 1;      // side effect: the CALLER's array is modified
  });
  return array;
};
    The test proves the mutation by calling it on constantArray twice and demanding [6, 8, 24, 5] both times. Use the method that returns a new array instead of editing one — map, from 1-8. Save. Success check: 2 failed, 3 passed.
  9. Function 4, addNumberArray, uses array.push(number) — a mutator (1-8's first family). Return a new array containing the old elements plus the new one; spread (2-6) does it in one expression. Save. Success check: 1 failed, 4 passed.
  10. Function 5, incrementObject, mutates the object it was handed. Copy it first — the shallow copy from Idea 2's aside — then increment every value on the copy and return that: 
    const incrementObject = (object) => {
  const copy = { ...object };     // your own object now; the caller's is untouched
  // …increment each value on `copy` (Object.keys + forEach, or build it fresh)…
  return copy;
};
    Save. Success check: Tests: 5 passed, 5 total — the whole suite green, with the test file never opened for editing.
  11. Prove to yourself the win is real: with the watcher still running, break one function on purpose (make addOne return n + 2) and save. 
    # no command — just edit and save, and read the watcher output
    You should see exactly one red test, naming exactly one function. Undo the break, save, and confirm you're back to 5 passed. That precision is what purity bought you.
  12. Quit the watcher and record the work (git from 1-5). This is your clone of someone else's repo — there's no remote of yours to push to and no PR to open, so this is the one place this week where committing straight to main is right; the branch-and-PR rule from 1-5 is about repos you own. Check what you're about to commit before you commit it: 
    # in the watcher tab: press q
git status               # modified: exercises/exercise1.js  — and NOTHING else
git add exercises/exercise1.js
git commit -m "Refactor exercise 1 functions to be pure"
    Success check: git status shows a clean tree, and the only file in the commit is exercises/exercise1.js. If that first git status lists test/exercise1.test.js as modified, you broke the workshop's one rule — restore it before committing: 
    git checkout -- test/exercise1.test.js   # throw away your edits, back to the shipped version
npm test                                 # must still be 5 passed
    (Already committed it by mistake? git checkout would only give you back your own version, since it is now what HEAD holds — reach one commit further back instead: git checkout HEAD~1 -- test/exercise1.test.js, then commit that restore.)

Check yourself — spot the side effect

Which of these four are pure, and for the impure ones, name the exact side effect:

const a = (arr) => arr.slice().sort();

const b = (arr) => arr.sort();

let count = 0;
const c = (n) => { count += n; return count; };

const d = (products, term) =>
  products.filter((p) => p.name.includes(term));
Reveal

a — pure. slice() with no arguments copies the array first, so sort reorders the copy. Same input, same output, caller untouched.

b — impure. sort mutates in place: the caller's array comes back reordered. (It's the sneakiest one on this list — sort looks like a transformer and isn't.)

c — impure. It edits the outer count, so c(1) returns 1, then 2, then 3. Both rules broken at once.

d — pure. filter returns a new array (1-8) and nothing outside is touched — and it's exactly the search function the week project needs.
