1-9 — Git Conflicts Workshop

~60 minutes · Week 1, Day 3 · Source: curriculum Day 3 git workflow workshop for two, adapted solo

Why this matters: the first time two branches disagree, git stops and asks you to decide — and it happens on every real team, usually in your first week. This workshop makes you cause a conflict on purpose, so the first one at a job is a chore, not a crisis.

Idea 1 — Where conflicts come from

You know from lesson 1-5 that work happens on branches and reaches main through pull requests. When git merges two branches, it combines their changes automatically — as long as they touched different lines. A merge conflict happens when the two branches made incompatible changes — by far the most common case, and the one this workshop causes, is both branches editing the same lines of the same file since they split: git has two versions and no way to know which one you meant, so it refuses to guess.

More examples (optional)

Which of these merge cleanly? All three start from the same commit:

  1. Branch A edits index.html, branch B edits style.css → no conflict: different files.
  2. Branch A edits the <h1> on line 9, branch B adds a <footer> on line 14 of the same file → no conflict: git merges line by line, and these lines don't overlap.
  3. Branch A and branch B both rewrite the <h1> on line 9 → conflict: two versions of one line.
  4. Bonus case you'll meet eventually: branch A edits a file that branch B deleted → also a conflict ("modify/delete") — git can't both keep and remove it.

Read more: Pro Git — basic branching & merging · GitHub — about merge conflicts

Idea 2 — Anatomy of a conflict, and the way out

A conflicted file is not broken — git writes both versions into it, fenced by markers, and waits:

<<<<<<< HEAD
<h1 class="page-heading">GIT WORKFLOW WORKSHOW</h1>     ← your current branch's version
=======
<h1 class="some-heading">GIT WORKFLOW WORKSHOP</h1>     ← the incoming branch's version
>>>>>>> main

Everything between <<<<<<< HEAD and ======= is the version on your branch (HEAD — the commit you're standing on); between ======= and >>>>>>> is the version you're merging in. Resolving means: edit the file to the text that should survive (yours, theirs, or a combination), delete all three marker lines, then git add and git commit — staging the file is how you tell git "decided". And if you ever open a conflict and panic: git merge --abort rewinds to the moment before the merge, losing nothing.

More examples (optional)

The same shape in CSS — you centered the heading, your teammate enlarged it:

<<<<<<< HEAD
h1 { text-align: center; }
=======
h1 { font-size: 3rem; }
>>>>>>> main

Both changes are wanted, so the resolution keeps both declarations and no markers:

h1 { text-align: center; font-size: 3rem; }

Editor note: VS Code detects the markers and shows "Accept Current / Accept Incoming / Accept Both" buttons above them — convenient, but it's doing exactly the edit-and-delete-markers routine you're learning by hand here.

Do it for real (~40 min)

You'll replay the curriculum workshop's scenario solo: a page ships with two bugs, two branches fix one bug each, and the second branch to land has to resolve the collision. Work in the workflow-practice repo you created and published in lesson 1-5, exercise 3.

  1. Start clean and current (the sync moves from 1-5): 
    cd ~/code/workflow-practice
git switch main
git pull                 # start from the latest main
git status               # nothing to commit, working tree clean
    Check: git status reports a clean tree on main.
  2. Set the stage — run the full 1-5 loop from memory (branch add-workshop-page → commit → push → PR → merge on GitHub → sync main; peek at the cheat sheet only if stuck). First open the ~/code/workflow-practice folder in your editor (File → Open Folder — it may still show week-1 from earlier lessons), then create and save this page there, with both bugs exactly as the workshop ships them — index.html: 
    <!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Git workflow workshop</title>
  <style>h1 { text-shadow: 2px 2px 5px grey; }</style>
</head>
<body>
  <h1 class="some-heading">GIT WORKFLOW WORKSHOW</h1>
</body>
</html>
    Bug 1: the heading says WORKSHOW. Bug 2: the client wants the class named page-heading, not some-heading. Success check: after your merge and sync, cat index.html on main shows the page, bugs and all.
  3. Create both fix branches now, from this same commit — that shared starting point is what makes them collide later. git branch NAME is new: it creates a branch without switching to it (1-5's git switch -c does both at once): 
    git branch fix-typo-heading        # create branch 1, stay on main
git branch update-class-heading    # create branch 2, also from this commit
git branch                          # lists main + both, * marks where you are
    You should see three branches listed, with * on main.
  4. Land the typo fix first: 
    git switch fix-typo-heading
    In your editor, fix only the typo: WORKSHOW → WORKSHOP. Save, then: 
    git add index.html
git commit -m "Fix typo in page heading"
git push -u origin fix-typo-heading
    Open the PR on GitHub and merge it, as in 1-5. Success check: the PR shows one changed line; after merging, index.html on GitHub says WORKSHOP.
  5. Sync your local main: 
    git switch main
git pull                 # brings down the merged typo fix
cat index.html           # heading now says WORKSHOP
    Check: the typo is gone on local main.
  6. Now the second fix — on the branch that never saw the first one: 
    git switch update-class-heading
cat index.html           # the typo is BACK — this branch split before the fix
    You should see WORKSHOW again. Nothing is lost — this branch is simply a snapshot from before the typo fix landed. In your editor, change only the class: some-heading → page-heading. Save, then: 
    git add index.html
git commit -m "Update class name in heading"
git log --oneline -1     # your class commit sits on top
    Success check: the newest commit is "Update class name in heading", and git status is clean.
  7. Bring main's progress into this branch — this is the collision, caused on purpose: 
    git merge main           # CONFLICT (content): Merge conflict in index.html
    You should see "Automatic merge failed; fix conflicts and then commit the result." That message is the workshop working, not you failing. (Escape hatch, any time before committing: git merge --abort.)
  8. Look before you touch — the safety ritual from 1-4 applies to merges too: 
    git status               # "Unmerged paths: both modified: index.html"
cat index.html           # see the conflict markers from Idea 2
    You should see your page-heading version fenced under <<<<<<< HEAD and main's WORKSHOP version under >>>>>>> main.
  9. Resolve it in your editor: both fixes are wanted, so the heading line becomes exactly 
    <h1 class="page-heading">GIT WORKFLOW WORKSHOP</h1>
    and the three marker lines are deleted. Save, then tell git you've decided: 
    git add index.html
git commit -m "Merge main, keeping both heading fixes"
git status               # clean again, back on update-class-heading
    Success check: cat index.html shows the one correct heading line and no <<<<<<< anywhere.
  10. Ship it and close the loop: 
    git push -u origin update-class-heading
    Open the PR — you should see GitHub report it has no conflicts (you already paid that bill locally). Merge it, then sync and tidy: 
    git switch main
git pull
git branch -d fix-typo-heading update-class-heading
git log --oneline --graph   # the diamond: two branches leaving main and rejoining
    Success check: GitHub's index.html has both fixes, and git branch lists only main.

Check yourself — predict the output

You're on branch polish-footer and run git merge main. The conflicted file shows:

<<<<<<< HEAD
<footer>© 2026 — built with coffee</footer>
=======
<footer id="contact">© 2026</footer>
>>>>>>> main

Which version is yours, which came from main, and what should the resolved line be if both changes matter?

Reveal

The HEAD side (top) is yours — HEAD is the branch you're standing on, polish-footer. The bottom side arrived from main. Keeping both changes: <footer id="contact">© 2026 — built with coffee</footer> — and all three marker lines deleted, then git add + git commit.
