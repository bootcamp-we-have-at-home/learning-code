2-2 — npm: Node's Package Manager

~35 minutes · Week 2, Day 1, 11:00–11:30 · Source: curriculum npm-introduction workshop

Why this matters: every tool you use from now on — Jest tomorrow, the week project's test suite, anything you clone from a job — arrives through npm. Half an hour here and the rest of the week is npm install and go.

Idea 1 — Node runs JS outside the browser; npm brings the packages

So far you have only ever run JavaScript inside a browser — the F12 console from lesson 1-1, and the page scripts from 1-10.

There is another place to run it: your own machine, with no browser open at all.

Node is the program that does that. It is the same JavaScript engine Chrome uses (V8), packaged on its own.

Node is the same JavaScript you already know. Nothing to relearn.

What changes is how you start it: node script.js runs a file, with no page and no browser.

Now the second half. Node ships with a companion command called npm.

npm downloads other people's ready-made code — packages — into your project, from a public registry of hundreds of thousands of them (npmjs.com).

On your side, three files and folders make up the whole system:

ThingWho creates itWhat it is
package.jsonnpm initYour project's ID card: name, version, scripts, and the list of packages it needs. You commit it.
node_modules/npm installThe actual downloaded package code. Huge, regenerable, never committed.
.gitignoreYouA list of paths git should pretend it can't see — node_modules goes in it.

Installing has two flavors. One flag is the whole difference:

npm install lodash        # a "dependency"    — the app itself needs it to run
npm install jest -D       # a "devDependency" — only YOU need it, while developing

Both land in node_modules. They just get recorded in different sections of package.json.

That record is the point.

A collaborator clones your repo (git clone, lesson 1-5) and gets no node_modules in it at all — because you never committed it.

They run npm install with no arguments. npm reads package.json and rebuilds the exact same environment.

Undeclared packages — ones you installed but that never made it into package.json — are how "works on my machine" happens.

More examples (optional)

A package.json after installing one of each, with the two sections side by side:

{
  "name": "shopping-cart",
  "version": "1.0.0",
  "dependencies": {                 // shipped to users — the app breaks without it
    "lodash": "^4.17.21"
  },
  "devDependencies": {              // dev-machine only — users never run the tests
    "jest": "^30.4.2"
  }
}

Deciding which flavor, by asking one question — does the running app need this?

npm install express            # a web server the app runs on   → dependency
npm install jest -D            # runs your tests                → devDependency
npm install eslint -D          # checks your code style         → devDependency
npm install cowsay -D          # a dev toy, as in this lesson   → devDependency

And what the ^ means in "^4.17.21": "this version or any later 4.x" — npm may install 4.18.0 on your collaborator's machine, but never 5.0.0, because a major-version bump is allowed to break things. That's semver.

Read more: npm docs — semantic versioning · npmjs.com (search a package before you trust it: weekly downloads, last publish date) · Node — what it is and why it exists

Idea 2 — npm scripts: named shortcuts that know where your tools live

In lesson 1-4 you typed terminal commands like ls and they simply worked, because your system already knows where those programs live.

Packages you install are different. Their command-line programs land in node_modules/.bin/, inside your project folder.

Your system doesn't look in there. So the raw way to run one is to spell out the whole path:

node_modules/.bin/cowsay hello        # works, but you must remember the path

Nobody types that twice. Instead you give the command a name in the "scripts" section of package.json:

{
  "scripts": {
    "greeting": "cowsay hello"        // "cowsay" alone is enough inside a script
  }
}

Then you run it by that name, from the project folder:

npm run greeting                      # npm looks up "greeting" and runs it

The short name works because npm puts node_modules/.bin on the path first, for as long as the script runs.

This is why every JS repo you'll ever clone has a README that says "run npm test" instead of a paragraph of paths.

It is also how you'll run Jest for the rest of the week.

More examples (optional)

A realistic scripts block — the same shape your week-2 project will end up with:

{
  "scripts": {
    "test": "jest",                   // npm test      — run the suite once
    "test:watch": "jest --watch",     // npm run test:watch — rerun on every save
    "lint": "eslint ."                // npm run lint  — check code style
  }
}

Two details worth knowing now:

  1. A handful of names are special and skip the word run: npm test and npm start work bare. Everything else needs npm run <name>.
  2. A script is just a shell line, so anything you learned in lesson 1-4 works in it — "clean": "rm -rf node_modules" is a valid (and destructive) script.

npm run with no name lists every script the project defines — the fastest way to orient yourself in a stranger's repo.

Read more: npm docs — scripts · npm docs — install (every flag, including -g)

Do it for real (~20 min)

This replays the workshop's eight tasks. Terminal moves (cd, mkdir -p, ls, cat) are all from lesson 1-4.

Part A — Get Node on the machine

  1. Week 1 never installed Node, so check before assuming. Type: 
    node -v      # prints a version like v22.14.0, or "command not found"
npm -v       # prints a version like 10.9.2, or "command not found"
    You should see two version numbers. If you got "command not found", do step 2; if both printed, skip to step 3.
  2. Install Node with your operating system's package manager. sudo runs the command as administrator and will ask for your login password (nothing appears as you type it — that's normal). Pick the one line that matches your machine: 
    sudo pacman -S nodejs npm        # Arch / Manjaro  ← this track's default
sudo apt install nodejs npm      # Debian / Ubuntu / Mint
brew install node                # macOS with Homebrew
node -v                          # verify
npm -v                           # verify
    Success check: both commands print a version number. (Node 20 or 22 is what this week's Jest 30 supports; 22 is the safest choice.) If none of those apply — Windows, or a distro that ships an ancient Node — use the official installer at nodejs.org/download and re-run the two -v checks afterwards.
  3. Meet the Node REPL — an interactive JavaScript prompt, the terminal's answer to the browser console from 1-1. Type node with no filename; the prompt changes to > and stays there, evaluating each line you type: 
    node               # your prompt becomes >
1 + 1              # 2
[1,2,3].map(n => n * 2)   # [ 2, 4, 6 ] — array methods from 1-8, no browser involved
.exit              # leave the REPL (Ctrl+D does the same)
    You should see results printed after each line, and your normal shell prompt back after .exit. If you ever find yourself stuck at a > that ignores your shell commands, that's the REPL — .exit.

Part B — A real project folder

  1. Create this week's workspace and the practice project inside it. You'll reuse ~/code/week-2 for the rest of week 2: 
    mkdir -p ~/code/week-2/npm-practice   # -p creates both levels
cd ~/code/week-2/npm-practice         # move in
pwd                                    # confirm where you are
ls -a                                  # nothing but . and .. — an empty folder
    You should see a path ending in /code/week-2/npm-practice and an empty listing. Now open this folder in your editor (File → Open Folder) — it will still be showing a week-1 folder, and you'll be editing files here for the rest of the lesson.
  2. Initialize the project. npm init on its own is interactive: it asks about a dozen questions (package name, version, description, entry point, …) with a suggested answer in parentheses, and Enter accepts each suggestion. The -y flag says "yes to all defaults" and skips the questions — use that: 
    npm init -y        # create package.json with default answers
cat package.json   # print what it made
    You should see a JSON object with "name": "npm-practice" (npm named it after the folder), a "version", and a "scripts" section containing a placeholder "test" entry. Nothing else exists yet.
  3. Install the workshop's package as a dev dependency: 
    npm install cowsay -D     # download cowsay, record it in devDependencies
    You should see npm report something like "added 41 packages, and audited 42 packages" (cowsay has dependencies of its own — that's the whole ecosystem arriving).
  4. See what changed in the project — the two halves of an install: 
    cat package.json          # a "devDependencies" block now lists cowsay
ls node_modules           # dozens of package folders, one per line
ls node_modules/.bin      # the runnable programs, including cowsay
    You should see "cowsay": "^1.6.0" (or similar) under devDependencies, and cowsay listed in .bin. Only the first of these gets committed.
  5. Run the tool the raw way, by its path: 
    node_modules/.bin/cowsay hello
    You should see an ASCII cow saying "hello". Remember this path — step 10 is about never typing it again.
  6. Keep the repo clean. node_modules is regenerable and can hold hundreds of thousands of files, so it never belongs in a commit (lesson 1-5: you commit sources, and anything committed is history forever). > replaces a file's whole content, so check first that nothing is there to lose: 
    ls -a                          # confirm there is no .gitignore yet
echo "node_modules" > .gitignore   # create it with one line
cat .gitignore                 # verify the content
    You should see no .gitignore in the first listing, then the single word node_modules printed back. Optional proof it works: git init then git status — the untracked list shows package.json, package-lock.json and .gitignore, but not node_modules.

Part C — Script it

  1. In your editor, open package.json and add a greeting entry to the existing "scripts" object — note the comma after the "test" line: 
    "scripts": {
  "test": "echo \"Error: no test specified\" && exit 1",
  "greeting": "cowsay hello"
},
    Save the file (autosave is off), then confirm from the terminal: 
    cat package.json     # the greeting script is in there
    You should see both script entries in the printed file. If npm later complains about invalid JSON, the culprit is almost always that missing comma.
  2. Run it by name: 
    npm run greeting     # npm resolves "cowsay" from node_modules/.bin
    Success check: the same cow, from a command with no path in it. That's the lesson.

Check yourself — fix the broken snippet

A teammate pushes this package.json. You clone the repo, run npm install, then npm test — and get jest: not found.

{
  "name": "cart",
  "version": "1.0.0",
  "scripts": {
    "test": "jest"
  },
  "devDependencies": {}
}

What's wrong, and what single command on the teammate's machine would have prevented it?

Reveal

The script calls jest, but no package declares it — devDependencies is empty, so npm install had nothing to fetch and node_modules/.bin/jest doesn't exist on your machine. It works for the teammate because they have Jest installed locally without it being recorded (likely installed globally with -g, or installed and then removed from the file).

The fix, run in the project: npm install jest -D — it downloads Jest and writes it into devDependencies, so the declaration travels with the repo. That's the difference between a package being on a machine and a package being part of a project.
