2-10 — Week Project: Ecommerce App (Tested, Pure, Persistent)

~2.5 days — most of the week's hours · Day 2 16:30 intro, Days 3–4 build, Day 5 09:00 code review → 10:00 respond to issues → 11:00 presentation (solo: written) · Source: curriculum week-2 project brief + the web-storage topic from research-afternoon.md

Why this matters: this is the first app in the mission with a tested core. Every rule you wrote a Jest test for in 2-3/2-4 now guards real shopping-cart logic.

It is also the portfolio piece that shows you can design code to be testable, not just make it work.

The brief (from the curriculum, in full)

An ecommerce app with two flows: a buyer and a seller.

Below are the brief's own user stories, copy-edited only for typos (the original writes "I want to able to search for item…"). Nothing has been added or removed.

They are your definition of scope: nothing more is required, nothing here is optional.

1. Buyer / Customer

  • I want to see all of the items available on the store
  • I want to be able to search for an item on the store by the name
  • I want to be able to filter items by the price or by category
  • I want to add an item to my cart
  • I want to be able to see the items inside my cart
  • I want to be able to delete any item inside my cart
  • I want to be able to see the total price of the items inside my cart
  • I want to be able to display the items either as a grid or a list

2. Seller

  • I want to be able to add my product (name, detail, price, image [link], and category) — the category must be a dropdown (a list of options), not a free-text field
  • I want to be able to see all of my products
  • I want to be able to search through my products
  • I want to be able to delete my own product
  • I want to be able to edit all the information of my product

Important note — the hard requirements. The brief lists three bullets; the third packs two separate requirements, so it is split in two here:

  • You should have pure functions
  • You should write a test for every function you have
  • The app should be responsive
  • …and should save its state even after closing the page (local storage)

How "a test for every function" is satisfied here. Taken literally it is impossible: you cannot meaningfully unit-test a function whose whole job is to paint the DOM.

The architecture in Idea 1 is what makes it achievable. Every function that decides anything lives in src/store.js and has a test, and src/app.js is kept so thin that it contains no decisions left to test.

That is the rule this project is marked against, and the same rule the done-checklist at the bottom states.

So if you find yourself wanting to test something in app.js, that is the signal to move the logic into store.js.

The brief's hints. A product is an object — the object literal shape from lesson 1-10. The brief sketches it as:

{
  id: 0,                  // unique — how delete/edit find this exact product
  name: "T-shirt",
  details: ".....",
  price: 25,
  // ...image link, category
}

It also points you at the methods you already own:

  • filter, map, includes — lesson 1-8
  • the spread operator ... — lesson 2-6
  • sort and concat — on the JavaScript cheat sheet; look them up, don't memorize them

Idea 1 — Architecture: a pure core with a thin dirty shell

In lesson 2-8 you split a function in two: the part that decides, and the part that touches the outside world. This project does the same thing to a whole app.

"Write a test for every function" is impossible if your functions read the DOM and write the DOM. It is easy once the deciding lives somewhere the DOM never reaches.

That split is the design rule of this project, not a suggestion:

LayerFileRuleTested?
Data / logicsrc/store.jsPure (2-8): takes data in, returns new data out. Never touches document, never touches localStorage, never mutates its arguments.Yes — a Jest test each (2-3)
Shell / renderingsrc/app.jsImpure and thin: reads inputs, calls a pure function, paints the result, saves to storage. Almost no ifs, no arithmetic.No — keep it too boring to break

Every pure function follows one shape: current state in, new state out.

Note that addToCart below returns a brand-new array via spread (2-6) instead of cart.push(...).

That is what makes it testable: the test can compare "before" and "after", because both still exist.

// src/store.js — pure. No document, no localStorage, no mutation.

const addToCart = (cart, product) => [...cart, product];        // NEW array, old cart untouched

const removeFromCart = (cart, id) => cart.filter(i => i.id !== id);

const cartTotal = (cart) => cart.reduce((sum, i) => sum + i.price, 0);
// reduce is 1-8's fold-into-one-value method: it walks the array carrying a
// running total (starting at the 0) and returns that single number at the end.

const searchByName = (products, query) =>
  products.filter(p => p.name.toLowerCase().includes(query.toLowerCase()));

const updateProduct = (products, id, changes) =>                  // the "edit all info" story
  products.map(p => (p.id === id ? { ...p, ...changes } : p));    // spread-merge, 2-6

if (typeof module !== "undefined") {              // the browser guard from 2-5:
  module.exports = { addToCart, removeFromCart, cartTotal, searchByName, updateProduct };
}                                                 // true in Node (Jest), false in a plain script tag

updateProduct is the whole edit feature in two lines, and it is the one you will reach for last (step 9).

map rebuilds the list, and { ...p, ...changes } makes a copy of the matched product with only the changed fields overwritten. Every other product comes back as the identical object.

Its test is a one-liner too: edit one product's price, assert the others came back unchanged.

The module guard at the bottom is not optional here. Same file, two runtimes, exactly as in 2-5's romanizer.js.

index.html loads store.js with a plain <script> tag — there is no bundler in this project. An unguarded module.exports throws ReferenceError: module is not defined in the browser, which stops the rest of the file from running.

Load order matters too: store.js before app.js, because app.js calls into it.

<!-- index.html, at the end of <body> -->
<script src="src/store.js"></script>   <!-- pure functions first... -->
<script src="src/app.js"></script>     <!-- ...then the shell that calls them -->

And the test for the first one — the test that would fail if someone "optimized" it into a push:

// src/store.test.js
const { addToCart } = require("./store");

test("addToCart returns a new cart without mutating the old one", () => {
  const cart = [];
  const shirt = { id: 1, name: "T-shirt", price: 25 };

  expect(addToCart(cart, shirt)).toEqual([shirt]);   // the new cart has it
  expect(cart).toEqual([]);                          // the ORIGINAL is untouched
});
More examples (optional)

The rest of the buyer flow's pure core, one function per user story — plus the seller's add and remove, which are the same two shapes again (updateProduct, the third, is in the body above):

const filterByCategory = (products, category) =>
  category === "all" ? products : products.filter(p => p.category === category);

const filterByMaxPrice = (products, max) => products.filter(p => p.price <= max);

const sortByPrice = (products) => [...products].sort((a, b) => a.price - b.price);
// spread FIRST: sort mutates, so sorting a copy keeps the function pure

const addProduct = (products, product) => [...products, product];

const removeProduct = (products, id) => products.filter(p => p.id !== id);

Contrast with the shell, which stays boring on purpose:

// src/app.js — impure, thin, untested
const onSearch = (event) => {                        // a callback, 2-1
  const results = searchByName(state.products, event.target.value);
  renderProducts(results);
};

Idea 2 — localStorage: making state survive a closed tab

Every page you have built so far forgets everything the moment you close the tab. The brief requires this one to remember.

Nothing in this week's sessions covered how. So the web storage research topic from research-afternoon.md is promoted to required material, and this section is it.

localStorage is a built-in object with two methods you need.

Try them in the browser console (F12, from lesson 1-1) on any page:

localStorage.setItem("greeting", "hello")   // save under a key
localStorage.getItem("greeting")            // → "hello"
localStorage.getItem("nothing-here")        // → null   (missing key, not an error)

The catch: it stores strings only. Hand it an array and you get useless text back. So every save/load round-trips through JSON:

const cart = [{ id: 1, name: "T-shirt", price: 25 }];

localStorage.setItem("cart", cart)                  // BAD → stored as "[object Object]"
localStorage.setItem("cart", JSON.stringify(cart))  // GOOD → stored as '[{"id":1,...}]'

JSON.parse(localStorage.getItem("cart"))            // back to a real array of objects

That gives the pattern the project needs — save on every change, load once at start:

// src/app.js — impure by design: this is the shell's job, not store.js's
const save = (key, value) => localStorage.setItem(key, JSON.stringify(value));

const load = (key, fallback) => {
  const raw = localStorage.getItem(key);
  return raw === null ? fallback : JSON.parse(raw);   // first-ever visit → fallback
};

const STARTING_PRODUCTS = [ /* the hard-coded products from step 4 */ ];

let state = {                                         // on start:
  products: load("products", STARTING_PRODUCTS),      // never stored yet → the starter list
  cart: load("cart", []),                             // never stored yet → an empty cart
};

// after ANY state change:
state = { ...state, cart: addToCart(state.cart, product) };
save("cart", state.cart);
renderCart(state.cart);

Notice the pure function still knows nothing about storage: addToCart computes the new cart, the shell persists it. That is the whole architecture in three lines.

The fallback argument matters as much as the key. On a brand-new browser there is nothing under "products", so whatever you pass as the fallback is what the shop opens with.

Pass [] and your step-4 products vanish the moment you add persistence.

load is the one place in app.js with a decision in it (the ? :), and that is deliberate. It decides nothing about your data, only whether the browser has any yet.

Everything about products, carts and prices still gets decided in store.js, where the tests are.

More examples (optional)

Run this in the console on your own page to feel the round-trip, one line at a time:

localStorage.setItem("cart", JSON.stringify([{ id: 1, price: 25 }]))
JSON.parse(localStorage.getItem("cart"))[0].price   // → 25, a real number again

localStorage.removeItem("cart")     // delete one key
localStorage.clear()                // delete EVERY key for this site — check what you'll lose first

Two traps worth meeting before they cost you an hour:

  • JSON.parse(null) returns null, but JSON.parse("") throws — hence the explicit raw === null check in load above rather than a truthiness test.
  • Opening your app as file:///… vs through a local server gives you two different storage buckets. Pick one way to open the app and stay with it, or your cart will seem to vanish.

You can inspect everything you've stored in DevTools (F12, 1-1) → Application tab → Local Storage — useful when the app loads state you didn't expect.

Do it for real — the build (~2 days)

Build in this order.

From step 4 onward, each step is a branch and a PR (lesson 1-5), each merged before the next starts, so main always runs.

Steps 1–3 are the repo baseline — an empty repo with no branches to merge into anything. So like the portfolio baseline in 1-11, they commit straight to main. That is the one declared exception.

Soft prerequisite: if you haven't done lesson 1-9 (git conflicts) yet, do it as catch-up first.

You merge a lot of PRs here, but none of them should conflict: you are the only committer, and each branch merges before the next starts. You'll hit your first real conflict eventually, and it shouldn't be here.

  1. Create an empty repo named ecommerce-app on GitHub (with a README), then clone it next to your other work (clone from 1-5, cd from 1-4): 
    cd ~/code
git clone URL             # URL from your new ecommerce-app repo
cd ecommerce-app
ls                        # README.md
    Success check: ls shows README.md. Now open this folder in your editor — File → Open Folder → ~/code/ecommerce-app (it probably still shows a week-2 exercise folder), so the files you save land in the repo.
  2. Make it an npm project with Jest (2-2 and 2-3): 
    npm init -y               # creates package.json
npm install --save-dev jest
    Then edit package.json so the test script is "test": "jest", and save the file. Success check: npm test runs and reports "No tests found" — that is Jest working, not failing.
  3. Keep node_modules out of git — it's thousands of files you never commit. Create a file named .gitignore in the repo root, containing exactly: 
    node_modules/
    Save it, then verify before you stage anything: 
    git status                # node_modules must NOT be listed
git add .gitignore package.json package-lock.json
git commit -m "Set up npm project with Jest"
git push
    Success check: git status shows .gitignore and the package files, and no node_modules. If node_modules still appears, fix .gitignore before committing — never git add . until it's clean.
  4. Build the page skeleton on a branch: semantic HTML (1-2) with a <header>, one <main>, a products <section>, a cart <aside>; flexbox layout (1-3) and mobile-first with at least one media query (1-6). Hard-code three fake products in an array in src/app.js and render them with map + a template literal (1-8, 1-10). 
    git switch -c product-list
# ...write index.html, style.css, src/app.js, save all files...
git add .
git commit -m "Render product list from data"
git push -u origin product-list
    Success check: opening index.html in the browser shows three product cards, and they reflow sensibly when you narrow the window.
  5. Buyer flow, one branch + PR per story, pure function first with its test (the red-green loop from 2-4), shell second: search by name → filter by price/category → add to cart → view cart → delete from cart → cart total. After each merge, sync and re-run everything: 
    git switch main
git pull
npm test                  # every test from every merged story still passes
    Success check after each merge: the suite is green and the app in the browser does one more thing than it did yesterday.
  6. Add persistence with the save/load pair from Idea 2 — save after every cart and product change, load once at startup. Move your step-4 hard-coded array into STARTING_PRODUCTS and pass it as load's fallback, so a first-time visitor still sees a stocked shop. Success check (the requirement, proven): your three products are still on the page, and after you add two items to the cart, close the tab entirely and reopen index.html, the cart and its total are still there.
  7. Add the grid/list toggle — one button that flips a CSS class on the products container, so the same cards lay out as a grid or a single column (flexbox from 1-3). The DOM move is classList, the same object 2-9's shipped blinkLight used to switch lights on and off with .add(name) and .remove(name) — and .toggle(name) is just those two in one call: it adds the class if the element doesn't have it, removes it if it does, which is exactly what one button needs. Add the button to index.html first — it doesn't exist yet — then grab both elements with querySelector (1-10): 
    <!-- index.html, just above the products section -->
<button id="view-toggle" type="button">Grid / list</button>
    const list = document.querySelector("#products");        // the products container
const button = document.querySelector("#view-toggle");   // the button you just added

button.addEventListener("click", () => {   // a callback, 2-1
  list.classList.toggle("grid");           // add "grid" if absent, remove it if present
});
    Success check: clicking the button switches layout, and the choice survives a refresh once you save it to storage too.
  8. Seller flow next: an "add product" form (name, details, price, image link, and category), the seller's own product list, search over it, and delete. It is the labelled-form pattern from 2-5 (<label for> + <input id>, submit listener, event.preventDefault()) with one new tag: the brief requires category to be a dropdown, which in HTML is <select> wrapping one <option> per choice. It is labelled and read exactly like an <input> — .value gives you the selected option's value attribute, as a string: 
    <label for="category">Category</label>
<select id="category" name="category" required>
  <option value="">Choose one…</option>      <!-- empty value + required = must pick -->
  <option value="clothing">Clothing</option>  <!-- value is what your JS reads... -->
  <option value="books">Books</option>        <!-- ...the text is what the user sees -->
</select>
    document.querySelector("#category").value   // → "books"  — a string, like input.value (2-5)
    Same discipline as every story: pure function + test, then wire the form. Success check: a product you add — with its category picked from the dropdown, never typed — appears in the buyer list, and is still there after a refresh.

    If you want more: MDN — the <select> element lists the extras (multiple, <optgroup>) this project does not need.

  9. Edit-a-product last — it is the fiddliest story, and it is the mirror image of reading the form. To pre-fill it you assign to the same .value you have been reading from, which puts text into the field and selects the matching <option>: 
    const product = state.products.find(p => p.id === id);    // find: like filter (1-8), but
                                                          // returns the FIRST match itself,
                                                          // not an array of matches
document.querySelector("#name").value = product.name;     // reading .value gets, assigning sets
document.querySelector("#category").value = product.category;   // selects that option
    Then on submit, don't add a second product — replace the existing one with updateProduct(products, id, changes) from Idea 1, and save the result. Success check: change a product's price and category; the buyer list, the cart total for new adds, and storage all agree, and the product count did not go up by one.
  10. Day 5, 09:00 — get reviewed. With the buyer flow merged, ask your teacher (the agent) to review the repo the way the curriculum's code review guide describes: it reads the README, runs npm test, and files GitHub issues phrased as questions with links to exact lines. Success check: at least three issues exist on your repo, and you understand each one.
  11. Day 5, 10:00 — respond to the issues. Reply in each issue thread first (agree, push back, or ask), then fix the ones you accept on a branch and let the PR close them for you. GitHub does that automatically if the PR description contains a closing keyword and the issue number — write it as one line in the description box when you open the PR: 
    Closes #12          # merging this PR closes issue 12. "Fixes #12" works the same way.
Closes #12, closes #14   # one keyword per issue if a PR settles several
    Answering is part of the etiquette; silently fixing is not. Success check: every issue is either closed by a merged PR or has your written reason for leaving it open.
  12. Day 5, 11:00 — the presentation, written. Solo, the cohort's demo becomes your README (same WHY / WHAT / HOW structure as the portfolio README in 1-11), plus two sections the cohort demo would have covered live: 
    ## Why        — the problem and who the two flows serve
## What       — the features, mapped to the user stories
## How        — architecture: pure core in src/store.js, thin shell in src/app.js, localStorage for state
## Run the tests
git clone URL && cd ecommerce-app
npm install
npm test

    Success check: a stranger could clone your repo, follow the README, and see a green test run without asking you anything.

Check yourself — the done checklist

This checklist is the check: every buyer story, every seller story, and the four hard requirements. Nothing here is optional, and every box maps to something the brief asked for.

  • Buyer: all items visible on load
  • Buyer: search items by name
  • Buyer: filter by price and by category
  • Buyer: add an item to the cart
  • Buyer: see the items inside the cart
  • Buyer: delete any item from the cart
  • Buyer: see the cart's total price, updating on every change
  • Buyer: toggle the display between grid and list
  • Seller: add a product with name, details, price, image link, and category — category chosen from a dropdown
  • Seller: see all own products
  • Seller: search own products
  • Seller: delete own product
  • Seller: edit all the information of a product
  • Pure functions — every function in src/store.js returns new data and mutates nothing (2-8)
