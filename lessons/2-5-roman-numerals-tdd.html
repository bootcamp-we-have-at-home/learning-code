2-5 — Roman Numerals: TDD Code-Along

~75 minutes · Week 2, Day 1, 15:00–17:00 · Source: curriculum bootcamp-we-have-at-home/Roman-Numerals code-along, adapted solo

Why this matters: FizzBuzz in 2-4 was TDD on a problem you already knew the answer to; this one is TDD on a problem where the algorithm genuinely arrives out of the tests. Then you wire the tested function to a real accessible form — the same "pure logic + thin DOM layer" split the week project is built on.

Idea 1 — A kata grows the algorithm out of the tests

A kata is a problem you solve for the practice, not the product. The roman-numerals kata (the repo credits Ray Sinnema) is the classic demonstration of TDD's central claim: if you only ever write the simplest code that turns the current red test green, the design shows up by itself.

Concretely: test 1 → "I" and you write return "I". That feels like cheating — it isn't, it's the rule. Test 2 → "II", 3 → "III" and the honest simplest fix is "repeat I that many times". Test 4 → "IV" and repetition breaks, so you special-case it. Test 5, 9, 10 and you're writing your fourth near-identical if — that repetition is the design pressure. You collapse the ifs into data: an array of objects pairing a number with its symbol (arrays of objects, dot access — lesson 1-10), walked largest-first. That table is the finished algorithm, and you never designed it up front.

Red → green → refactor: the third step is the one people skip. Refactoring means changing the shape of the code while the tests stay green — the tests are what make it safe, which is the entire payoff of having written them first (2-3).
More examples (optional)

The subtractive pairs are the whole trick. Roman numerals are written largest-first and additively — MDCLXVI = 1000+500+100+50+10+5+1 — except for six cases where a smaller symbol sits in front and is subtracted:

4    IV     // 5 - 1
9    IX     // 10 - 1
40   XL     // 50 - 10
90   XC     // 100 - 10
400  CD     // 500 - 100
900  CM     // 1000 - 100

The trick that makes the code trivial: stop treating them as exceptions and put them in the table as ordinary entries, each just above the value it subtracts from. Then one greedy loop handles both cases:

1994
  - 1000 M    → "M",        994 left
  -  900 CM   → "MCM",       94 left
  -   90 XC   → "MCMXC",      4 left
  -    4 IV   → "MCMXCIV",    0 left   // done

Same walk for 2024: M, M (1000 twice), then X, X, then IV → MMXXIV.

Read more: Dave Thomas — Code Kata (where the practice-problem idea comes from) · kata-log.rocks (a catalogue to keep repping) · Fowler — opportunistic refactoring

Idea 2 — From tested function to page: an accessible form

The converter is pure logic, so it belongs in its own file with its own tests. The page is a separate, thin layer: take input, call the function, show the result. Three pieces you need for that layer.

1. A labelled input. Lesson 1-2 made the case that tags should say what they mean and that accessibility is checkable with Lighthouse; forms are where that bites hardest. Every input needs a <label> whose for matches the input's id — that pairing is what a screen reader announces, and it also makes clicking the label focus the input. A placeholder is not a label.

<label for="numeral">Enter a number (1–3999)</label>
<input id="numeral" name="numeral" type="text" placeholder="e.g. 42" required>
<!-- id is what the label points at; name is the key the browser would submit under -->
<button type="submit">Convert</button>

2. The submit event. A form's default behaviour is to send its data to a server and reload the page — which throws away your result instantly. You listen for submit on the form (not click on the button: that way Enter in the field works too) and cancel the default:

form.addEventListener("submit", (event) => {   // the arrow is a callback — 2-1
  event.preventDefault();                      // stop the page reloading
  // …read the input, call romanizer, show the result
});

3. Writing the result into the DOM — document.querySelector plus .textContent, exactly as in 1-10.

More examples (optional)

Reading the typed value. .value is always a string, even from type="number" — which is why the converter starts by running its input through Number():

const input = document.querySelector("#numeral");
input.value            // "42"  — a string, always
Number(input.value)    // 42    — a number
Number("abc")          // NaN   — "not a number", the value the guard tests for

Proof that preventDefault() is doing something: comment it out, submit, and watch the URL gain ?numeral=42 and the page blink — that's the browser navigating away with your form data.

One more accessibility touch the repo's page doesn't have: mark the result box as a live region so screen-reader users hear the answer appear:

<div class="result" role="status" aria-live="polite"></div>

Read more: MDN — your first form · MDN — event.preventDefault() · W3C — labelling controls

Do it for real (~50 min)

This is the code-along, and this page is the presenter: each numbered step hands you the next test case, you make it pass before reading on. Resist scrolling ahead — the point is to feel the design pressure build, not to arrive at the answer.

You are not cloning the curriculum repo to work in: it ships the finished converter and its 27 passing tests (verified by cloning it while writing this lesson), so cloning it would hand you the answer before you've felt the problem. You'll scaffold fresh, the same way you did in 2-3, and read the original as a solution afterwards.

  1. Make the project folder and scaffold Jest (mkdir and cd are from 1-4; the npm commands are from 2-2 and 2-3): 
    mkdir -p ~/code/week-2/roman-numerals   # -p: create week-2 too if it isn't there yet
cd ~/code/week-2/roman-numerals
npm init -y                             # writes package.json with defaults
npm install --save-dev jest             # installs the test runner into node_modules/
                                        # same audit summary as 2-3; never run --force
    You should see npm report the added packages, and ls shows package.json, package-lock.json, node_modules.
  2. Open this folder in your editor — File → Open Folder → ~/code/week-2/roman-numerals (it will still be showing whatever 2-4 left open, and autosave is off, so every step below ends with save the file). In package.json, find the "scripts" block npm init -y wrote and replace only the line inside it so it reads: 
    "scripts": {
  "test": "jest"
},                    <-- keep this comma: more fields follow it in the file
    JSON has no comments and no forgiveness — every entry except the last needs its trailing comma, and a missing one makes npm test answer with EJSONPARSE instead of running. Save, then check it runs: 
    npm test          # "No tests found" — that's the correct answer right now
    You should see Jest start and report no tests found, exiting with an error. Jest works; you have nothing to run yet.
  3. Red #1. Create romanizer.test.js with the first case only, and save: 
    const romanizer = require("./romanizer");   // pulls in the file you're about to write

test("1 → I", () => {
  expect(romanizer(1)).toBe("I");
});
    Run npm test. You should see it fail with Cannot find module './romanizer'. A missing file is a perfectly good red.
  4. Green #1 — the simplest thing that works. Create romanizer.js, save, rerun: 
    function romanizer(num) {
  return "I";                 // yes, really. Simplest code that passes the test.
}

module.exports = romanizer;   // makes it importable by the test file
    You should see 1 passed. It is obviously incomplete — the next test is what makes it grow.
  5. Start the watcher so you stop retyping npm test. This is an interactive program: it takes over the terminal, reruns on every save, and waits with a menu (Watch Usage: Press a to run all tests… Press q to quit). Leave it running in this terminal and edit files in the editor; press q (or Ctrl+C) to exit when you're done. 
    npx jest --watchAll        # rerun every test on every save; q to quit
    You should see the green result redraw within a second of you saving a file.
  6. Red #2 — repetition. Add these two tests, save, watch them fail, then make all three pass: 
    test("2 → II", () => {
  expect(romanizer(2)).toBe("II");
});

test("3 → III", () => {
  expect(romanizer(3)).toBe("III");
});
    Simplest honest implementation: build a string of num copies of "I" (a loop, or "I".repeat(num)). Success check: 3 passed. Don't peek ahead — the next case is designed to break exactly this.
  7. Red #3 — the first exception. Add it, save: 
    test("4 → IV", () => {
  expect(romanizer(4)).toBe("IV");
});
    Your repeat gives "IIII". Fix it the crude way — an if (num === 4) return "IV"; before the loop. Success check: 4 passed, and you're now looking at a special case you know will multiply.
  8. Red #4 — it multiplies. Add all four at once and make them pass, still crudely (more ifs, string concatenation, whatever gets to green): 
    test("5 → V",   () => { expect(romanizer(5)).toBe("V"); });
test("6 → VI",  () => { expect(romanizer(6)).toBe("VI"); });
test("9 → IX",  () => { expect(romanizer(9)).toBe("IX"); });
test("10 → X",  () => { expect(romanizer(10)).toBe("X"); });
    Success check: 8 passed and a function you'd be embarrassed to show anyone. That embarrassment is the signal to refactor.
  9. Refactor — the table. Green tests are a safety net: rewrite the body freely, and the moment you save, Jest tells you whether you broke anything. Replace all the branches with the lookup table (an array of objects, largest value first — 1-10) and one greedy walk: 
    const NUMERALS = [
  { value: 10, symbol: "X" },
  { value: 9,  symbol: "IX" },     // subtractive pairs sit just above what they subtract from
  { value: 5,  symbol: "V" },
  { value: 4,  symbol: "IV" },
  { value: 1,  symbol: "I" },
];

function romanizer(num) {
  let remaining = num;
  let result = "";
  NUMERALS.forEach(({ value, symbol }) => {   // forEach + a callback — 1-8 and 2-1
    while (remaining >= value) {              // take this symbol as often as it fits
      result += symbol;
      remaining -= value;
    }
  });
  return result;
}

module.exports = romanizer;
    Success check: still 8 passed, zero test edits. You changed the design without changing the behaviour — that is the refactor step, and it only felt safe because the tests existed.
    The { value, symbol } in the parameter list is destructuring — 2-6 covers it properly tomorrow. If it distracts you, write (entry) => and use entry.value / entry.symbol instead; identical behaviour.
  10. Now growing is free. Add these, save, and notice you fix them by editing data, not logic — new rows in NUMERALS, still largest-first: 
    test("14 → XIV",     () => { expect(romanizer(14)).toBe("XIV"); });
test("40 → XL",      () => { expect(romanizer(40)).toBe("XL"); });
test("90 → XC",      () => { expect(romanizer(90)).toBe("XC"); });
test("400 → CD",     () => { expect(romanizer(400)).toBe("CD"); });
test("1987 → MCMLXXXVII", () => { expect(romanizer(1987)).toBe("MCMLXXXVII"); });
test("3999 → MMMCMXCIX",  () => { expect(romanizer(3999)).toBe("MMMCMXCIX"); });
    (Rows you'll need: 1000 M, 900 CM, 500 D, 400 CD, 100 C, 90 XC, 50 L, 40 XL — work out the order yourself before adding them.) Success check: 14 passed, and romanizer(14) passed without you touching a line of the loop.
  11. Guard the edges — the repo's converter answers with a message instead of nonsense. Add these, then make them pass with two early returns at the top of the function: 
    test("0 is out of range",    () => { expect(romanizer(0)).toBe("out of range"); });
test("4000 is out of range", () => { expect(romanizer(4000)).toBe("out of range"); });
test("'abc' is not a number",() => { expect(romanizer("abc")).toBe("Not a Number"); });
test("'42' from an input field still works", () => { expect(romanizer("42")).toBe("XLII"); });
    That last one matters for the next section: form fields hand you strings. Your parameter is still called num, so start the function body with const n = Number(num); and work from n after that — return "Not a Number" when Number.isNaN(n), return "out of range" when n <= 0 || n > 3999, and convert n. Success check: 18 passed. Press q to leave the watcher.
  12. Wire it to a page. Create index.html in the same folder and save it: 
    <!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Roman numeral converter</title>
</head>
<body>
  <main>
    <h1>Roman numeral converter</h1>
    <form id="converter">
      <label for="numeral">Enter a number (1–3999)</label>
      <input id="numeral" name="numeral" type="text" placeholder="e.g. 42" required>
      <button type="submit">Convert</button>
    </form>
    <div id="result" role="status" aria-live="polite"></div>
  </main>
  <script src="romanizer.js"></script>
  <script src="app.js"></script>
</body>
</html>
    You should see, on opening the file in the browser, a labelled field and a button — and clicking the label text should focus the field (that's the for/id pairing working).
  13. Make romanizer.js safe to load in a browser. module.exports is a Node idea (2-2); in a plain <script> there is no module, so that line throws ReferenceError: module is not defined in the console. Guard it — change the last line of romanizer.js to: 
    if (typeof module !== "undefined") {   // true in Node (Jest), false in the browser
  module.exports = romanizer;
}
    Save, run npm test once more. Success check: still 18 passed, and reloading the page no longer shows ReferenceError: module is not defined in the console (F12, from 1-1). One error remains — a 404 for app.js, because you haven't written it yet. That one disappears in the next step.
  14. Handle the submit. Create app.js, save, reload the page: 
    const form = document.querySelector("#converter");
const result = document.querySelector("#result");

form.addEventListener("submit", (event) => {
  event.preventDefault();                              // don't reload the page
  const typed = document.querySelector("#numeral").value;
  result.textContent = romanizer(typed);               // the function your tests proved
});
    Success check: type 1987, press Enter (not just the button) — MCMLXXXVII appears below the form, the URL does not change, and the page does not blink. Try abc and 5000: you get the guard messages, straight from the tested function.
  15. Optional, 2 minutes, good habit: put it under version control with the 1-5 loop. First protect yourself from committing thousands of dependency files: 
    ls                       # look before you commit: node_modules is huge
echo "node_modules" > .gitignore   # creates .gitignore (overwrites it if it exists — it doesn't yet)
git init
git add .
git status               # verify: NO node_modules paths listed
git commit -m "Roman numeral converter, built test-first"
    Success check: git status before committing lists your source files and .gitignore, and nothing from node_modules.

Check yourself

1. Predict the output. Using the finished table, trace the greedy walk by hand before running anything:

romanizer(14)
romanizer(40)
Reveal

"XIV" — 14 ≥ 10 → X, 4 left; 4 is less than 10, 9, 5, but 4 ≥ 4 → IV, 0 left.

"XL" — the walk hits the 40 row before the 10 row (largest first), so it takes XL once and finishes with 0 left. Without that row it would produce "XXXX": the row order is the algorithm.

2. Fix the broken snippet. All the "simple" values are here and the loop is fine, but three tests fail: 4 gives "IIII", 9 gives "VIIII", 40 gives "XXXX". What's missing, and where exactly does it go?

const NUMERALS = [
  { value: 100, symbol: "C" },
  { value: 50,  symbol: "L" },
  { value: 10,  symbol: "X" },
  { value: 5,   symbol: "V" },
  { value: 1,   symbol: "I" },
];
Reveal

The subtractive pairs are missing. Each one goes immediately above the value it is built from, so the greedy walk meets it first:

{ value: 100, symbol: "C" },
{ value: 90,  symbol: "XC" },   // added: above 50, so 90 is matched before L
{ value: 50,  symbol: "L" },
{ value: 40,  symbol: "XL" },   // added: above 10, so 40 doesn't become XXXX
{ value: 10,  symbol: "X" },
{ value: 9,   symbol: "IX" },   // added
{ value: 5,   symbol: "V" },
{ value: 4,   symbol: "IV" },   // added
{ value: 1,   symbol: "I" },

Put XL below X instead and 40 still comes out "XXXX" — the walk consumes the 40 with four Xs before it ever reaches the XL row.
