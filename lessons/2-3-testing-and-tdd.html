2-3 — Testing & TDD: Your First Jest Test

~45 minutes · Week 2, Day 1, 11:30–12:00 · Source: curriculum testing-tdd-intro

Why this matters: the curriculum's own line for this week is "refactoring your code without tests in place is like playing Russian roulette" (learning-outcomes.md).

Everything you build from here — the week project, the API week, every job — gets changed after it's written, and tests are what let you change it without fear.

Idea 1 — What a test is, and what "unit" means

You have been testing all week already. Every time you opened the F12 console from lesson 1-1, called a function, and eyeballed the result — that was a test.

The curriculum defines it plainly: testing is the process of executing your code to check it does what it's supposed to do.

What you were doing has a name: a manual test. It works, and it evaporates the moment you close the tab.

An automated unit test is that same check written as code, so it can be re-run in one second, forever.

Here is the idea with no framework at all — pure JavaScript you could already write after 1-7:

const double = (num) => num * 2;

const testDouble = () => {
  const actual = double(2);        // run the thing
  const expected = 4;              // say what it should be
  if (actual !== expected) {       // === / !== comparison from 1-7
    console.log(actual + " should equal " + expected + " ✗");
  } else {
    console.log("Test passed ✔");
  }
};

A framework like Jest is only that pattern, prewritten and prettier.

"Unit" means the thing under test is one small piece — a single function such as double.

Its opposite is an integration test, which checks that several pieces fit together.

This week is unit tests only: small functions, called directly, with a known answer.

The coursebook writes its examples with function declarations and var; today we write const + arrow functions (from 1-7 and 1-8) — same behavior, less noise.
More examples (optional)

Three checks on the same function, written the manual way — notice that the only things changing are the input and the expected value:

const shout = (word) => word.toUpperCase() + "!";

shout("hi")     // expect "HI!"    — normal case
shout("")       // expect "!"      — empty input, the classic edge case
shout("Hi!")    // expect "HI!!"   — does it double the punctuation? decide, then test

Writing them out is how you discover that the third case is a requirements question, not a coding question. That discovery-before-code effect is the whole argument for TDD in Idea 2.

And the unit/integration line in one concrete pair: "does calculateTotal([2, 3]) return 5?" is a unit test; "does clicking Add to cart update the on-screen total and what's saved in the browser?" is an integration test.

Idea 2 — TDD and the red-green-refactor cycle

In Idea 1 the check came second: double existed first, and testDouble was written afterwards to confirm it. That is the obvious order.

Test-Driven Development inverts it: you write the test before the function exists.

That sounds backwards until you notice what it forces. To write expect(add(2, 2)).toBe(4) you must first decide the function's name, its arguments, and its return value.

Requirements get settled while they are still cheap to change.

The loop has three beats:

BeatYou doWhy
RedWrite one failing testProves the test can fail — a test that passes before the code exists is testing nothing
GreenWrite the simplest code that passes itSmallest step that could work; no extra features
RefactorTidy the code while the test stays greenSafe cleanup — the test tells you the second you break something

Then repeat for the next requirement.

A good test also reads like a bug report. It answers three questions: what is being tested, what should it do, what did it actually do.

Jest gives you all three for free — the first two from the name you type, the third from its failure output.

More examples (optional)

One full cycle in miniature, for a isEven function:

// RED — the test exists, the function does not
test("2 is even", () => {
  expect(isEven(2)).toBe(true);
});
// run it: fails, "isEven is not defined"

// GREEN — the simplest thing that passes
const isEven = (n) => true;        // yes, really: it passes the one test you wrote

// RED again — add the case that exposes the cheat
test("3 is not even", () => {
  expect(isEven(3)).toBe(false);
});

// GREEN — now the real implementation is forced
const isEven = (n) => n % 2 === 0;

That deliberately silly => true step is a real TDD teaching move: it shows that your tests, not your intentions, define what "done" means. If a stupid implementation passes, you are missing a test.

Do it for real (~25 min)

You'll build a tiny project from nothing, write a test for a function that doesn't exist, watch it fail, and then make it pass.

Nothing here is a new tool: npm init and npm install are exactly as lesson 2-2 taught them, and the terminal moves (mkdir, cd, ls, cat) are from 1-4.

  1. Make the project folder inside your week-2 workspace (created in 2-2) and move into it: 
    mkdir -p ~/code/week-2/jest-practice   # -p: create parents if missing
cd ~/code/week-2/jest-practice
pwd                                    # confirm where you are
    You should see a path ending in /code/week-2/jest-practice.
  2. Create the package.json that marks this folder as an npm project (2-2): 
    npm init -y     # -y accepts every default instead of prompting
cat package.json
    You should see a small JSON object with "name": "jest-practice" and "version": "1.0.0".
  3. Install Jest as a dev dependency: 
    npm install -D jest     # -D  = --save-dev
                        # "19 high severity vulnerabilities" at the end is expected
ls                      # package.json, package-lock.json, node_modules
    You should see npm report roughly added 294 packages, then a new node_modules folder and "jest" listed under devDependencies in package.json.
    npm ends every Jest install with an audit summary — currently 19 high severity vulnerabilities. It is counting advisories in small packages that Jest itself depends on, not in anything you wrote, and none of them run in a browser or on a server here. Never run the npm audit fix --force npm suggests: "force" gives it permission to install a different major version of Jest, which is how a working test setup breaks. Expect this same summary in every lesson that installs Jest this week.
  4. Open this folder in your editor — File → Open Folder → ~/code/week-2/jest-practice. It probably still shows a week-1 project, and autosave is off, so you must save every file before running anything.

    Then edit package.json so the scripts block reads:

    "scripts": {
  "test": "jest"
},
    Save the file. Success check: cat package.json shows "test": "jest" where the generated placeholder used to be.
  5. Now the TDD part: write the test first. Create add.test.js with exactly this, and save: 
    const add = require("./add");          // pull in the file we haven't written yet

test("adds two numbers", () => {       // name = "what should it do?"
  expect(add(2, 2)).toBe(4);           // run it, assert the result
});
    Then check what's on disk: 
    ls
    You should see a new add.test.js alongside package.json, package-lock.json and node_modules — and no add.js. That missing file is intentional.
  6. Run the tests and get red on purpose: 
    npm test        # runs the "test" script, i.e. jest
    You should see a failure naming exactly what's missing — Cannot find module './add' from 'add.test.js', and a red summary line Test Suites: 1 failed, 1 total with Tests: 0 total. (Zero tests, not one failed test: the require blew up before Jest ever got to register your test(...) block — that is what a missing-module red looks like.) This is the method working, not you failing: red proves the test is really checking something.
  7. Green. Create add.js with the simplest thing that could pass, and save: 
    const add = (a, b) => a + b;

module.exports = add;      // hand this value to whoever require()s this file
    Then: 
    npm test
    You should see ✓ adds two numbers and Tests: 1 passed, 1 total. You have completed one red-green cycle.
  8. Feel the safety net — break the code deliberately and watch the test catch it. Change add.js to (a, b) => a * b, save, then: 
    npm test        # predict: does the test catch the sabotage?
    You should see it still passes — because 2 * 2 is also 4. That is a missing test, not a working function. Add a second case to add.test.js, save, and run again: 
    test("adds two different numbers", () => {
  expect(add(2, 3)).toBe(5);
});
    Success check: Jest now reports Expected: 5 / Received: 6 — the bug report writes itself. Restore a + b, save, and confirm both tests pass.
  9. Meet the two matchers you'll otherwise get wrong. Add to add.test.js, save, and run npm test: 
    test("toBe vs toEqual", () => {
  expect([1, 2]).toEqual([1, 2]);      // passes — compares CONTENTS
  expect([1, 2]).toBe([1, 2]);         // FAILS  — compares identity, like ===
});
    This is the by-reference comparison from 1-7: two separately-built arrays are never === to each other. You should see the toEqual line pass and the toBe line fail with Jest suggesting "use toEqual". Delete this test when you've seen it, save, and get back to green.
    Rule of thumb: toBe for numbers, strings, booleans; toEqual for arrays and objects; toBeNull when the answer should literally be null. The rest live on the cheat sheet — look them up, don't memorize them.

Check yourself — predict the output

A folder contains these two files, both saved, with Jest installed and "test": "jest" set:

// greet.js
const greet = (name) => {};
module.exports = greet;

// greet.test.js
const greet = require("./greet");

test("greets by name", () => {
  expect(greet("Amjad")).toBe("Hello, Amjad!");
});

You run npm test. Does it pass or fail, and what does Jest report?

Reveal

It fails — red, one test failed. The require works fine (the file exists this time), the function runs fine, but a function body of {} returns undefined, so Jest prints roughly:

● greets by name

  expect(received).toBe(expected)

  Expected: "Hello, Amjad!"
  Received: undefined

Two failure shapes to recognize from now on: Cannot find module = the file or export is missing; Expected/Received = the file is there and the logic is wrong. And the green version is one line: const greet = (name) => `Hello, ${name}!`; — the template literal from 1-10.
