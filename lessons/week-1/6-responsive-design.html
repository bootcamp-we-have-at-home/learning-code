1-6 — Responsive Design

~45 minutes · Week 1, Day 2 · Source: curriculum Day 2 Responsive Design workshop

Why this matters: the Week 1 project is judged on desktop and mobile views. Most of your visitors — and every interviewer who opens your portfolio on a phone — see the mobile layout first.

Idea 1 — One page, many screens

A responsive page adapts its layout to the screen instead of assuming a desktop. Two ingredients you already half-have:

  1. The viewport meta tag — without it, phones render a zoomed-out desktop page: 
    <meta name="viewport" content="width=device-width, initial-scale=1">
  2. Layouts that flex — your flex-wrap from lesson 1-3 is already responsive behavior.
More examples (optional)

What "assuming a desktop" fails like, concretely:

  1. No viewport tag: a phone pretends to be ~980px wide, renders the desktop layout, then shrinks it — your visitor sees a postage stamp and pinch-zooms to read. (This is the bug you'll fix in step 3.)
  2. Fixed widths: main { width: 960px; } forces sideways scrolling on any screen narrower than 960px. Responsive habit: max-width: 960px; width: 100%; — cap it, never demand it.
  3. Fixed columns: three cards locked side by side become three unreadable slivers on a phone — unless flex-wrap (lesson 1-3) lets them drop into a column, which is exactly what your .cards rule already does.

Read more: web.dev — Learn Responsive Design · MDN — responsive design overview

Idea 2 — Media queries, mobile-first

A media query applies CSS only when a condition holds:

/* base rules: written for small screens first */
nav { flex-direction: column; }

/* from 40rem wide and up, override */
@media (min-width: 40rem) {
  nav { flex-direction: row; }
}

Mobile-first means the plain rules serve the smallest screen and min-width queries add complexity as space grows — simpler than desktop-first with max-width overrides, because the base case is the simple layout. (BEM naming and deeper responsive patterns are this week's research-afternoon topics.)

More examples (optional)

The same design written both ways — count the rules:

/* mobile-first: base is the simple stack, ONE query adds the row */
.cards { display: flex; flex-direction: column; gap: 1rem; }
@media (min-width: 40rem) {
  .cards { flex-direction: row; }
}
/* desktop-first: base is the complex layout, the query UNDOES it */
.cards { display: flex; flex-direction: row; gap: 1rem; flex-wrap: wrap; }
@media (max-width: 40rem) {
  .cards { flex-direction: column; flex-wrap: nowrap; }
}

Both work; the second one makes you write the complex case first and then subtract. Queries also aren't only about width — @media (prefers-color-scheme: dark) is how this very lesson page switches to a dark palette (peek at assets/course.css).

Read more: Luke Wroblewski — Mobile First (the 2009 essay the term comes from, and why it helps with media queries) · MDN — using media queries (every condition beyond min-width)

Do it for real (~25 min)

Two threads from here on: the CSS work, and putting ~/code/week-1 under git with the commands from lesson 1-5 — like everything you'll ever build from now on.

  1. Open a terminal and type: 
    cd ~/code/week-1   # enter the profile page folder
pwd                # confirm the location
git init            # initialize git
    You should see "Initialized empty Git repository…".
  2. Snapshot the page as it stands: 
    git add index.html
git commit -m "Profile page from lessons 1-2 and 1-3"
git status          # nothing to commit, working tree clean
    Check: git status now says "nothing to commit, working tree clean".
  3. Add the viewport meta tag inside <head>, next to <meta charset>: 
    <meta name="viewport" content="width=device-width, initial-scale=1">
    Success check: save, refresh, then press F12, click the phone/tablet icon (device toolbar), pick a phone — text is readable, not a zoomed-out miniature.
  4. Make the nav mobile-first by changing your nav rule (keep the other declarations): 
    nav {
  display: flex;
  gap: 1rem;
  flex-direction: column;
}
    Save, refresh in phone view. You should see the links stacked vertically.
  5. Add the desktop override at the end of your <style> block: 
    @media (min-width: 40rem) {
  nav { flex-direction: row; justify-content: flex-end; }
}
    Success check: save, refresh, then drag the device-toolbar width (or toggle it off): links stack when narrow, become a right-aligned row when wide.
  6. Give the project cards a minimum dignity by adding this to .cards article: 
    min-width: 15rem;   /* keep cards from squeezing too thin */
    Save, refresh. You should see (in phone view) the cards refuse to squeeze thinner and wrap into a column instead — flex-wrap from 1-3 doing the work.
  7. Commit the responsive changes (everything saved? git status should show index.html modified): 
    git add index.html
git commit -m "Make profile page responsive"
git log --oneline       # show both commits
    Check: git log --oneline shows both commits.
  8. Publish the repo — from memory of exercise 2 in lesson 1-5: create an empty week-1 repository on GitHub (no checkboxes), then, in the same terminal, confirm your location and run the three "push an existing repository" lines GitHub shows: 
    pwd   # should end in /code/week-1
git remote add origin …
git branch -M main
git push -u origin main
    Success check: your page's code is visible on GitHub. Lesson 1-10 opens a pull request against this very repo.

Check yourself — predict the output

Screen is 30rem wide. Base rule says nav { flex-direction: column; }; a @media (min-width: 40rem) block says row. Which applies, and what if the screen grows to 45rem?

Reveal

At 30rem the query condition is false, so the base column applies. At 45rem the query matches and its row rule wins because it comes later in the stylesheet. Mobile-first in one sentence: base = small screen, queries = progressively wider.
