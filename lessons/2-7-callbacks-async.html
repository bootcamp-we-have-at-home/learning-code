2-7 — The Call Stack, Sync vs Async & setTimeout

~60 minutes (26 of them a video) · Week 2, Day 2, 10:30–13:00 · Source: curriculum intro-to-functions-slides.md (second half, "Funception" onward) + the scheduled video "What the heck is the event loop anyway?"

Why this matters: lesson 2-1 taught you what a callback is; this one teaches when your code actually runs — the difference between "the next line" and "later". Week 3 is API week: every request you fire returns later, and code that assumes otherwise silently reads the wrong value.

Idea 1 — Nested calls and the call stack

In lesson 1-7 you already called one function from inside another, and it simply worked. This section is about what JavaScript is doing while that happens — with a CS degree behind you this is a refresh, not a lecture.

Start with the deck's trap. Three functions that only log, nested inside each other:

function foo1(x) { console.log("foo1 got:", x); }
function foo2(x) { console.log("foo2 got:", x); }
function foo3()  { console.log("foo3 ran"); }

foo1(foo2(foo3()));   // logs "foo3 ran", then "foo2 got: undefined", then "foo1 got: undefined"

Two things fall out of that line.

Order. Arguments must be evaluated before the call that uses them. So the innermost function runs first, even though foo1 is written first.

The undefineds. A function with no return returns undefined — the value type from lesson 1-7.

So nesting log-only functions passes nothing useful along: typeof foo3() is "undefined", not "function".

Fix it by returning instead of logging — the deck's corrected chain:

function foo1() {
  const x = foo2();
  return x * 3;
}

function foo2() {
  const y = foo3();
  return Number(y);   // Number() is built in: turns the string "1" into the number 1
}

function foo3() {
  return "1";         // a STRING, deliberately
}

foo1();               // 3
The coursebook writes var x = foo2(); today we write const — 1-7's const-by-default rule. Same behavior.

While foo1() is running, none of these three functions have finished yet. JavaScript keeps track of that with the call stack.

Every call puts a frame on top of the stack: foo1 first, then foo2, then foo3. They come off in the opposite order — foo3 returns "1" and pops, only then can foo2 compute Number("1") and pop, and only then does foo1 return 3.

JavaScript has exactly one call stack. So exactly one thing is ever running, one frame at a time.

That stack has a size limit. A function that calls itself with no exit condition pushes frames until the engine gives up with RangeError: Maximum call stack size exceeded — a stack overflow, which is where the website got its name.

More examples (optional)

Reading a stack in DevTools. Paste this into the browser console (the F12 console from lesson 1-1):

function a() { b(); }
function b() { c(); }
function c() { throw new Error("boom"); }
a();

The error's stack trace prints c, then b, then a — top of stack first. That trace is the call stack at the moment it blew up, which is why reading traces bottom-up tells you how you got there.

And the overflow, on purpose (harmless — the engine stops it):

function forever() { return forever(); }
forever();   // RangeError: Maximum call stack size exceeded

Idea 2 — Callbacks more than one layer deep

In lesson 2-1 you passed a function to another function as an argument — a callback. The rule you used there: hand over the function's name, with no parentheses on it.

That works fine one layer deep:

function firstFunction() {
  console.log("I'm the first function");
}

function secondFunction(callback) {
  callback();
  console.log("I'm the second function, I expect a callback as input");
}

function thirdFunction(callback) {
  callback();
  console.log("I'm the third function, I also expect a callback as input");
}

secondFunction(firstFunction);   // first, then second — works

Now try two layers the obvious way, and watch it break:

thirdFunction(secondFunction(firstFunction));
// logs first, then second... then TypeError: callback is not a function

Same rule as Idea 1: the argument is evaluated first. So secondFunction(firstFunction) actually runs here, logs its two lines, and returns undefined.

thirdFunction therefore receives undefined and tries to call it. Hence the TypeError.

The fix is to hand thirdFunction something callable that does that work later — wrap it:

thirdFunction(() => secondFunction(firstFunction));
// first, second, third — in that order

The load-bearing takeaway: to go more than one layer deep in callbacks, wrap the inner call in an anonymous function. You will use this in every step of the rest of this lesson, and in week 3's callback workshop.

The coursebook writes the wrapper as function () { secondFunction(firstFunction) }; today we write the arrow () => secondFunction(firstFunction). Identical here — you'll see both forms in real code.

Callbacks can also take arguments — the caller decides what to pass them:

function firstFunction(number) {
  console.log("I'm the first function, I expect an input:", number);
}

function secondFunction(callback) {
  const number = 1;
  callback(number);        // secondFunction supplies the argument
}

secondFunction(firstFunction);      // "…input: 1"
secondFunction(firstFunction(1));   // TypeError: callback is not a function

That last line breaks for the by-now-familiar reason: firstFunction(1) runs immediately and returns undefined.

You never call a callback yourself when handing it over. You pass the name, and the receiving function decides when — and with what — to invoke it.

More examples (optional)

You have already written wrapped callbacks without noticing. In 1-8, nums.map(n => n * 2) passes an arrow because n * 2 alone would be evaluated on the spot — the arrow is exactly the "do it later, with the argument you give me" wrapper from this section.

Three layers, same pattern, nested:

thirdFunction(() => secondFunction(() => firstFunction()));

And the DOM version you met in 1-10 — the browser is the caller, and it passes the event object into your callback whenever the click happens:

button.addEventListener("click", (event) => {
  console.log("clicked", event.target);   // you pass the function; the browser calls it later
});

Idea 3 — Synchronous vs asynchronous, and setTimeout

Every example so far ran top to bottom, and you could predict the order just by reading down the page.

That has a name: synchronous. Each action completes before the next one starts, and the stack empties in order.

Asynchronous code is the other kind. It doesn't wait.

Take a concrete case. Your page asks a server for a list of products (week 3's job), and the response takes 400 ms.

If that wait were synchronous, the single call stack would be blocked for 400 ms: no clicks, no scrolling, frozen page.

So instead you hand the request a callback and carry on. When the data arrives, your callback is run.

Which raises the question the video answers: if there is only one call stack, who runs the callback later, and when exactly?

Watch this now — it is a scheduled part of the curriculum, 26 minutes, and it is the single best explanation of this topic that exists: Philip Roberts, "What the heck is the event loop anyway?" (JSConf EU). He builds a live visualizer of the call stack, the queue, and the loop. Watch it before the do-it-for-real steps below; they assume it.

Here is the short version, so the vocabulary is already anchored when you watch.

Timers, network requests and DOM events are provided by the browser — not by the JavaScript language itself.

So when you call setTimeout, the browser starts a timer outside the stack, and setTimeout returns immediately.

When that timer finishes, your callback is put in a callback queue — a line of callbacks waiting for a turn.

The event loop has one job: take the first callback off that queue and push it onto the call stack.

It does that only when the stack is empty — only once all your currently-running synchronous code has finished.

setTimeout(() => console.log("later"), 1000);   // returns instantly; logs after ~1s
console.log("now");                             // runs first — "now", then "later"

Two consequences worth memorizing:

  • The delay is a minimum, not a promise. setTimeout(fn, 0) still runs after all your synchronous code, because the queue is only drained on an empty stack.
  • An async value doesn't exist on the next line. A value produced inside a callback isn't there yet on the line after the call — the deck's trap, which you'll run yourself in step 5.
More examples (optional)

Two timers plus synchronous work — predict, then run:

console.log("1");
setTimeout(() => console.log("2"), 500);
setTimeout(() => console.log("3"), 0);
console.log("4");
// 1, 4, 3, 2 — both timers wait for the stack to empty; then 0ms beats 500ms

Blocking, made visible. This one freezes the tab for ~3 seconds — the timer callback cannot run even though its 0 ms elapsed long ago, because the stack is busy:

setTimeout(() => console.log("I waited for the stack"), 0);
const stop = Date.now() + 3000;
while (Date.now() < stop) {}     // busy-wait, blocks everything
console.log("blocking finished");

The log order is "blocking finished", then "I waited for the stack" — the exact demo the video draws.

Do it for real (~40 min, 26 of them the video)

No new project folder for this lesson — everything runs in a REPL. Use either:

  • the browser console — F12 from lesson 1-1, "Console" tab. Multi-line snippets: press Shift+Enter for a new line, Enter to run. Chrome may ask you to type allow pasting once before it accepts a pasted block.
  • the Node REPL — from lesson 2-2: run node in your terminal, and the prompt changes to >. Type a line, press Enter, and it prints the value. Exit with .exit or Ctrl+D.

Predict the output before pressing Enter on every step — that prediction is the whole exercise.

  1. The Oops version — nested log-only functions: 
    function foo1(x) { console.log("foo1 got:", x); }
function foo2(x) { console.log("foo2 got:", x); }
function foo3()  { console.log("foo3 ran"); }

foo1(foo2(foo3()));
    You should see three lines in the order foo3 ran, foo2 got: undefined, foo1 got: undefined — innermost first, and nothing useful passed along.
  2. The corrected, return-based chain. Redefine all three (a fresh console tab avoids clashing with step 1's definitions): 
    function foo3() { return "1"; }
function foo2() { const y = foo3(); return Number(y); }
function foo1() { const x = foo2(); return x * 3; }

foo1();          // ?
typeof foo3();   // ?
    Success check: foo1() returns 3, and typeof foo3() is "string" — not "undefined" like step 1's version.
  3. Break the two-layer callback, then fix it. Define the three functions from Idea 2, then run the broken line first: 
    thirdFunction(secondFunction(firstFunction));   // logs two lines, then throws
    You should see the first and second functions' logs, then TypeError: callback is not a function. Now the fix: 
    thirdFunction(() => secondFunction(firstFunction));
    Success check: three lines, first → second → third, no error.
  4. Watch "What the heck is the event loop anyway?" — 26 minutes, all of it. Success check: without re-reading Idea 3, you can say out loud what the call stack, the callback queue, and the event loop each do, and why setTimeout(fn, 0) is not "run now".
  5. The sync/async mixing trap from the deck. Run these three lines as one block, then wait 3 seconds: 
    function asyncAddOne(number, callback) {
  setTimeout(() => callback(number + 1), 3000);
}

let x = 0;
asyncAddOne(10, (newValue) => { x = newValue; });
console.log(x);   // 0 or 11?
    You should see 0. asyncAddOne returned instantly, having only scheduled the callback; console.log(x) ran while the stack was still busy, three seconds before x was assigned. (The coursebook uses var x; let is 1-7's reassignable form.)
  6. Prove the value does arrive — move the log inside the callback: 
    let y = 0;
asyncAddOne(10, (newValue) => { y = newValue; console.log("inside callback:", y); });
    Success check: nothing for ~3 seconds, then inside callback: 11. The rule: to use an async result, put the code that uses it inside the callback.
  7. Confirm that zero is not zero: 
    setTimeout(() => console.log("timeout 0"), 0);
console.log("synchronous");
    You should see synchronous first, then timeout 0.
  8. Capstone — the deck's challenge. Define both functions exactly as given (don't modify them), then chain them so the final log is (10 + 1) * 3: 
    function asyncAddOne(number, callback) {
  setTimeout(() => callback(number + 1), 3000);
}

function asyncMultiplyThree(number, callback) {
  console.log("result from first function:", number);
  setTimeout(() => callback(number * 3), 3000);
}

// your code here: log the final result
    Success check: after ~3 seconds you see result from first function: 11, and ~3 seconds later final result: 33. Give it a real attempt before opening the reveal — this is the exact shape week 3's API code takes.
    Reveal the solution 
    asyncAddOne(10, (newNumber) => {
  asyncMultiplyThree(newNumber, (result) => {
    console.log("final result:", result);
  });
});

    Read it as Idea 2's rule applied twice: you can't write asyncMultiplyThree(asyncAddOne(10), …), because asyncAddOne returns undefined immediately. The only place 11 exists is inside the first callback — so the second call has to happen in there. Nesting callbacks like this is why the pattern is nicknamed "callback hell"; promises (week 3) are the cure.

  9. Close the REPL when you're done, so your terminal is a shell again and not a JavaScript prompt (the next lesson starts with cd ~/code, which a Node REPL would read as JavaScript and reject): 
    .exit                            # Node REPL only; Ctrl+D does the same
    Success check: the > prompt is gone and your normal shell prompt is back. (Browser-console students: just close DevTools with F12.)

Check yourself — predict the output

console.log("A");

setTimeout(() => console.log("B"), 0);

function slow() { return "C"; }
console.log(slow());

setTimeout(() => console.log("D"), 10);

Write down the four letters in the order they log, and one sentence saying why.

Reveal

A, C, B, D. A and C are synchronous, so they run to completion on the call stack first — slow() pushes and pops a frame before console.log prints C. Both timers were handed to the browser, and their callbacks only reach the stack once it is empty: B (0 ms) was queued before D (10 ms), so it goes first.
