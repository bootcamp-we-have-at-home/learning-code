2-4 — FizzBuzz: TDD Workshop (Ping-Pong)

~60–90 minutes · Week 2, Day 1, 13:00–15:00 · Source: curriculum workshop bootcamp-we-have-at-home/fizzbuzz, adapted solo

Why this matters: lesson 2-3 taught you what a Jest test looks like; this is the first time you build a whole function without ever writing implementation code before a failing test demands it. That reflex is what makes the week project (2-10) testable instead of hopeful.

Idea 1 — Ping-pong: two hats, never worn at once

Ping-pong is the pairing form of the red-green-refactor cycle from lesson 2-3. Partner A writes one failing test and hands the keyboard over. Partner B writes the minimum code that makes it pass — deliberately literal, even silly — then writes the next failing test and hands back. The point isn't politeness: B's "cheating" implementation is a bug report against A's test. If return 1 passes your whole suite, your suite is too small, and you found that out in ten seconds instead of in production.

Solo adaptation — you wear both hats, one at a time. Say the hat out loud before each move, and physically change something (sit back, move to the other file, switch terminal tab) so the switch is real:

  • Tester hat: open test.js only. Write one test(...) block. Say what failure you expect ("this will fail: expected 1, received undefined"). Run it. You must be wrong-free about the failure before you fix it.
  • Implementer hat: open index.js only. Write the laziest code that turns the suite green. Hard-coding is not just allowed, it's the discipline — it proves what the next test has to cover.

The one rule that makes this work: never write implementation while wearing the tester hat. If you catch yourself typing if (n % 3 === 0) inside test.js, you've slipped.

More examples (optional)

A ping-pong exchange on a different kata — add(a, b):

// Tester hat — test.js
test("adds 2 and 2", () => {
  expect(add(2, 2)).toBe(4);     // fails: add is not defined
});

// Implementer hat — index.js  (laziest thing that passes)
const add = () => 4;             // green. yes, really.

// Tester hat — the lazy version is now a bug report: write the test that kills it
test("adds 2 and 5", () => {
  expect(add(2, 5)).toBe(7);     // fails: got 4
});

// Implementer hat — now the shortcut is impossible
const add = (a, b) => a + b;     // green, and honestly general

Notice the shape: the second test exists because the first implementation was lazy. That's ping-pong doing your test design for you.

Idea 2 — Refactoring under green

Refactor means: change how the code is written without changing what it does. The reason TDD makes it safe is timing — you only refactor when every test passes. The suite is your undo detector: change the shape, re-run, and if a test goes red you broke behavior and you know it within seconds. Refactoring on red is guessing; refactoring on green is engineering.

In this workshop the refactor moment is small and specific: in iteration 5, once every test is green, three near-identical if blocks collapse into one ordered chain. That is a behavior-preserving edit you make with a green suite watching. Earlier edits — like generalising () => 1 into (n) => n — look similar but are not refactors: they happen on red and add behavior a new test demanded.

The coursebook's snippets use function fizzbuzz(n) { … } and module.exports; today we write const fizzbuzz = (n) => { … } with arrow functions (lesson 1-8) — same behavior, and the export line stays exactly as the repo ships it.
More examples (optional)

A behavior-preserving refactor, with the suite green before and after:

// green — but repetitive
const label = (n) => {
  if (n === 0) { return "none"; }
  if (n === 1) { return "one"; }
  return "many";
};

// refactored — same outputs for every input, fewer branches
const NAMES = ["none", "one"];
const label = (n) => NAMES[n] ?? "many";

How you know it's a refactor and not a rewrite: you did not touch test.js. The moment a "refactor" needs a test changed, it's a behavior change wearing a disguise.

Do it for real (~60 min)

You'll build FizzBuzz from nothing but tests, in the curriculum's own repo. The spec, from the workshop README: fizzbuzz(n) returns the number itself for most inputs, "Fizz" for multiples of 3, "Buzz" for multiples of 5, and "FizzBuzz" for multiples of both. Don't read ahead to the finished algorithm — the exercise is the order.

  1. Clone the workshop into your workspace (git clone is from lesson 1-5; it creates a folder named after the repo): 
    cd ~/code                                          # the workspace from lesson 1-4
git clone https://github.com/bootcamp-we-have-at-home/fizzbuzz.git   # creates ~/code/fizzbuzz
cd fizzbuzz
ls                                                 # index.js  test.js  package.json  ...
    You should see index.js, test.js and package.json listed.
  2. Install the project's declared dependencies — Jest is listed in package.json, not yet on disk (lesson 2-2: npm install with no package name installs what the project already declares): 
    npm install       # reads package.json, downloads Jest into node_modules/
                  # audit summary at the end: expected, see the 2-3 note; never --force it
    Success check: npm prints an "added N packages" line and ls now shows a node_modules folder and package-lock.json.
  3. See the starting state before you change anything (the look-first ritual from lesson 1-4): 
    npm test          # runs the "test" script from package.json → jest
    You should see one green test called Testing Jest is working — the placeholder the repo ships, which asserts 2 + 2 === 4 and proves the runner works. That is your baseline; the repo's index.js holds an empty fizzbuzz that returns nothing yet. Now open the folder in your editor: File → Open Folder → ~/code/fizzbuzz (it probably still shows a week-1 project). Autosave is off — every step below means save the file before running anything.
  4. Start the workshop rhythm: watch mode. Open a second terminal tab and leave the watcher running in it for the rest of the lesson. A new tab always starts in your home folder, so the first thing it needs is the cd from 1-4 — otherwise npm looks for a package.json that isn't there and errors with ENOENT: no such file or directory, open '…/package.json': 
    cd ~/code/fizzbuzz      # the new tab starts in ~, not in the repo
npm test -- --watch     # the -- passes --watch through npm to jest
    Jest runs once, then parks on an interactive menu: Press a to run all tests, f to run only failed ones, p to filter by filename, q to quit, Enter to re-run now. It re-runs by itself every time you save. You should see the results redraw within a second of saving a file; press q to exit whenever you're done.
    --watch uses git to decide which files changed; if it complains about that, use npm test -- --watchAll instead.
  5. Iteration 1 — red. Tester hat: test.js only. Replace its contents with: 
    const fizzbuzz = require("./index.js");   // pulls in the implementation file

test("returns the number for 1", () => {
  expect(fizzbuzz(1)).toBe(1);
});
    Save. You should see watch mode go red with Expected: 1 / Received: undefined — the shipped fizzbuzz exists but its body is empty, so it returns undefined (the second failure shape from 2-3). Say the failure out loud before moving on; a test that fails for the reason you predicted is a working test.
  6. Iteration 1 — green. Implementer hat: index.js only, and write the laziest code that passes. Literally this: 
    const fizzbuzz = () => 1;    // yes, hard-coded. it's the minimum.

module.exports = fizzbuzz;
    Save. Success check: watch mode flips to green, 1 test passing. You now have a deliberately stupid function — that's the setup for the next test.
  7. Iteration 2 — red, then green. Tester hat: add a second test to test.js (keep the first): 
    test("returns the number for 2", () => {
  expect(fizzbuzz(2)).toBe(2);       // fails: received 1
});
    Save; you should see 1 passing, 1 failing. Implementer hat: the hard-code is now impossible, so generalise in index.js: 
    const fizzbuzz = (n) => n;   // red → green: the second test forced a general shape
    Success check: 2 tests passing. Note what that edit was and wasn't: it went red → green by adding the behavior the new test demanded, so it is the green step, not a refactor. Your first real refactor-under-green — reshaping code while the suite is already all-green — comes in iteration 5.
  8. Iteration 3 — multiples of 3 → "Fizz". Tester hat first, always: 
    test("returns Fizz for multiples of 3", () => {
  expect(fizzbuzz(3)).toBe("Fizz");
  expect(fizzbuzz(9)).toBe("Fizz");   // a second multiple keeps you honest
});
    Save and watch it go red (received 3). Implementer hat: add the minimum branch to index.js — one if, using the remainder operator % from lesson 1-7 (n % 3 === 0 means "3 divides n exactly"). Success check: 3 tests green, and tests 1–2 still pass — never let an old test go red to make a new one pass.
  9. Iteration 4 — multiples of 5 → "Buzz". Same rep, your turn to write both halves unaided: a red test for fizzbuzz(5) and fizzbuzz(10), then the minimum branch in index.js. 
    expect(fizzbuzz(5)).toBe("Buzz");    // the assertion your new test needs
    Success check: 4 tests green.
  10. Iteration 5 — multiples of both → "FizzBuzz". Tester hat: 
    test("returns FizzBuzz for multiples of 3 and 5", () => {
  expect(fizzbuzz(15)).toBe("FizzBuzz");
  expect(fizzbuzz(30)).toBe("FizzBuzz");
});
    Save. You should see it fail with received "Fizz" — because 15 hits your %3 branch first. Implementer hat: fix it, then refactor under green — with the whole suite passing, tidy the branches into one readable ordered chain and re-run. Success check: 5 tests green both before and after the refactor; test.js untouched by the refactor.
  11. Challenge — negative numbers. The README's stretch: decide the spec first (is fizzbuzz(-3) "Fizz", or should negatives be rejected?), write it down in one sentence, then drive it with tests: 
    expect(fizzbuzz(-3)).toBe("Fizz");   // or whatever your written spec says
expect(fizzbuzz(-1)).toBe(-1);
    Success check: the suite is green and your index.js matches the sentence you wrote — not the other way round.
  12. Commit the work on a branch, the loop from lesson 1-5 (press q in the watch tab first, or switch back to your first tab — it is already sitting in ~/code/fizzbuzz): 
    git switch -c tdd-fizzbuzz
git status                       # node_modules is NOT listed (.gitignore handles it),
                                 # but package-lock.json IS: npm install wrote it and
                                 # this repo doesn't ship one
git add index.js test.js package-lock.json
git commit -m "Build fizzbuzz test-first through five iterations"
git status                       # verify
    Success check: the second git status says nothing to commit, working tree clean, and git log --oneline -1 shows your commit. (This repo is the course's, not yours, so you can't push to it — pushing needs your own fork; skip it unless you want the extra rep.)

Check yourself — which tests catch which implementation?

Here are three candidate implementations and a test list. For each implementation, say which tests pass and which fail — reason it out before revealing.

// tests
expect(fizzbuzz(2)).toBe(2);            // T1
expect(fizzbuzz(3)).toBe("Fizz");       // T2
expect(fizzbuzz(5)).toBe("Buzz");       // T3
expect(fizzbuzz(15)).toBe("FizzBuzz");  // T4

// A
const fizzbuzz = (n) => {
  if (n % 3 === 0) return "Fizz";
  if (n % 5 === 0) return "Buzz";
  if (n % 15 === 0) return "FizzBuzz";
  return n;
};

// B
const fizzbuzz = (n) => {
  if (n === 3) return "Fizz";
  if (n === 5) return "Buzz";
  if (n === 15) return "FizzBuzz";
  return n;
};

// C
const fizzbuzz = (n) => {
  if (n % 15 === 0) return "FizzBuzz";
  if (n % 3 === 0) return "Fizz";
  if (n % 5 === 0) return "Buzz";
  return n;
};
Reveal

A — T1, T2, T3 pass; T4 fails (returns "Fizz": 15 is a multiple of 3, so the first branch wins and the %15 line is unreachable). Order matters.

B — all four pass, and the function is still wrong: fizzbuzz(6) returns 6, fizzbuzz(9) returns 9. This is exactly the lazy-implementer move from Idea 1 — a green suite proves your tests, not your code. Adding a second multiple per rule (9, 10, 30) is what kills it.

C — all four pass, and it generalises: the most specific rule is checked first. This is the shape your iteration-5 refactor should land on.
